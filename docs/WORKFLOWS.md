# 1.0 目標、修復、規劃與通知

桌面「專案設定」可編輯既有專案、命令、啟用狀態、範圍、優先序與交付分支；保留未修改的設定與 `{config_dir}` 命令模板。儲存前核對設定版本，避免覆寫另一次修改。

## 獨立審查與修復

`quality.enabled` 啟用時，執行器完成後先執行指定測試，再以全新的唯讀 Codex 回合審查變更。結構化 findings 的 P0–P2 阻擋交付；缺失、矛盾、無法核對的結果亦不交付。測試與審查綁定待交付的 Git 內容樹。驗證後的內容、分支或提交若改變，不能推送。

測試或審查指出問題時，最多執行 `max_repairs`（0–3）次修復，每次重新測試及審查。測試／審查程序自行改寫內容屬完整性錯誤，停止而不自動修復。每次開發嘗試的有限修復與每任務的中斷重試是不同上限；兩者都受暫停、模型服務狀態與用量預算控制。

開發、審查、修復、規劃都有獨立用量記錄與 JSONL 路徑；工作嘗試與規劃工作各有可繼承程序鎖。規劃不假裝成開發嘗試，也不把未回報用量當零。桌面「用量與預算」可逐回合開啟記錄與保存人工核對依據。

## GitHub CI 修復

`ci_repair.enabled` 只處理 APEE 已交付、仍開放、目前 head／分支／base 仍對應驗證版本的 PR。先核對 GitHub Actions 執行版本及 repository，再取得失敗日誌；工作尚未啟動、日誌缺失或來源不同時不呼叫修復模型。平台拒絕啟動時顯示 GitHub 的診斷；APEE 不修改帳戶付款或支出設定。

修復使用原 PR 分支與固定 head 的全新 checkout，強制重新測試及獨立審查，再更新同一 PR。只允許原 head 的後續提交，核對遠端版本並以精確 lease 保護競爭寫入。來源變更、分支刪除、PR 關閉或他人提交都停止更新。模糊寫入結果以現有 PR 與提交核對，不重跑模型或建立第二個 PR。

`max_attempts_per_pr`（1–3）為跨重啟、跨提交的累計修復任務上限。同時只會保留一項處理中的修復；失敗後可在剩餘上限內重試相同來源。原始提交、測試與觀察保留，`active_delivery` 連結新驗證紀錄，沒有把舊測試改稱新版本通過。

## 目標與依賴

「目標與依賴」設定目標、完成條件、專案、優先序與候選入列政策，並連結尚未開始的任務及其前置工作。依賴可跨專案；未知任務、自我依賴與循環皆拒絕。前置成果須合併且版本核對仍有效；本機成果需你檢查並明確確認，確認時再次核對測試、審查與工作副本。

排程依目標、專案及任務優先序選擇，保存派工決策及目標快照。未啟用的專案／目標、未完成依賴、同時推進專案上限均有可見原因。已開始而等待本機驗收或 PR 審查的專案佔用容量；關閉、合併或明確接受本機成果後釋放。

## 回饋、規劃與成效

「回饋與成效」保存使用者提供的來源與帶時區的觀測時間。指標定義包含目標、專案、單位、`lte`／`gte` 方向及十進位目標值。原始回饋與觀測不能覆寫；測量方式改變時新增定義，同一指標／時間的矛盾數值會被拒絕。

明確按「依目前資料規劃」可執行一次規劃，不會啟用背景規劃。`planning.enabled` 控制每輪自動規劃；每 UTC 日期的模型回合、新工作及待決候選各有上限。全新唯讀規劃回合只能引用已提供的目標、專案與證據識別碼；不能捏造數據。相同輸入不反覆呼叫，重複標題不重複建立候選，等待交付／成效的目標不持續產生待辦。

目標預設 `autonomy: "propose"`，候選需你接受並記錄原因才加入正常佇列。只有明確設定 `enqueue` 的目標可自動入列；仍遵守所有開發與預算政策。

接受候選時保存當時指標基準。完成交付後，只比較相同定義、交付後且晚於基準的觀測。結果區分等待觀測、達標、未達標與退步；合併本身不表示產品成功，指標達標亦不自動宣稱因果歸因。未設定真實數據時保持未知。驗收用的合成資料與生產資料分開。

## macOS 成果通知與服務

「審查與通知」提供審查、CI、規劃政策、首次背景服務安裝、更新、啟停及移除。macOS 通知由原生 `UNUserNotificationCenter` 送出，需在桌面允許並啟用；沒有可用 app 或未啟用時不發送。通知只使用本機管道。

有意義的任務、PR、候選、成效與容量變化進入 SQLite 佇列。以 instance、主題及變化序號去重，原 PR 與 CI 修復任務不重複通知相同成果；過期訊息可被新狀態取代。程序有帶 token 的暫時領取及送達確認，失敗退避重試，次數耗盡可由桌面明確重試並保存歷史。重啟後先核對通知中心／待發的相同識別碼，再決定是否提交。

`delivered` 表示已核對現有通知或系統接受提交；實際橫幅、聲音與使用者是否看見仍依 macOS 設定與專注模式。若系統已接受而程序未記錄，且使用者同時移除通知，重新啟動仍可能重送；不宣稱跨系統絕對一次送達。

CLI 的 `portfolio`、`project-edit`、`configure` 與 `notifications` 和桌面共用同一設定、資料及規則。`portfolio status` 提供完整目標資料；`snapshot` 仍只讀本機資料，不呼叫模型或 GitHub。

審查／規劃介面依 [Codex 官方非互動模式](https://learn.chatgpt.com/docs/non-interactive-mode)；CI 日誌依 [GitHub CLI](https://cli.github.com/manual/gh_run_view) 與 [Actions workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs)；通知依 [Apple 授權介面](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:)) 與 [既有通知查詢](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getdeliverednotifications(completionhandler:))。

# Autonomous Project Evolution Engine

## 已確認的方向

使用者有許多專案，管理負擔過重。第一優先是 **自動完成開發任務、執行測試，交付待審變更**。專案主要位於 GitHub，已指定來源帳號 `irons163`。

APEE 持續維護任務背景、執行進度與驗證結果，讓使用者將注意力放在方向、取捨與成果審查。專案清單是入口，實際交付工作是第一版核心。

## 第一版的使用體驗

1. 加入想交由 APEE 處理的 repository，指定測試與準備方式。
2. 提供具體任務，或在 GitHub Issue 加上派工標籤。
3. APEE 依專案優先順序，為任務建立獨立 checkout。
4. 執行器修改程式；引擎另外執行測試並保存證據。
5. 通過後產生本機審查包，或依專案設定自動交付 Draft PR。
6. 使用者檢查成果。後續輪次從持久佇列繼續，不重複執行已處理的工作。
7. APEE 更新 PR 檢查、審查與合併狀態，把需處理的成果集中顯示。

日常入口未來應集中顯示「已完成的成果」「需要你決定的事」「下一批工作」。目前以中文總覽與命令列提供相同的基本資訊。

## 系統邊界

| 元件 | 第一版責任 |
| --- | --- |
| 專案設定 | Repository、啟用狀態、優先順序、準備與測試命令、Draft PR 交付設定 |
| GitHub 介面 | 專案清單、分頁 Issue 同步、來源狀態核對、任務分支與 Draft PR |
| 任務佇列 | 任務去重、固定需求快照、狀態、每次嘗試與事件記錄、每日嘗試上限 |
| 連續執行器 | 有限輪次、總嘗試上限、可持久保存的暫停、服務錯誤後停止派工 |
| 執行器 | 接收工作要求，在獨立 checkout 中修改程式，回傳執行記錄 |
| 驗證器 | 在明確權限的命令環境執行專案指定測試，核對驗證前後的內容版本 |
| 交付器 | 保存 patch、審查說明與提交，核對遠端寫入結果 |
| 成果追蹤 | 讀取已交付 PR 的檢查、審查、版本與合併狀態，保存觀察與變化 |

模型負責完成具體工作；任務是否可以交付，由引擎根據實際結果判定。引擎不把模型說「完成了」直接視為驗證成功。

## 已實作的工作狀態

`queued → preparing → running → testing → ready → publishing → review`

- `queued`：等待執行的已入列任務。
- `preparing`：核對來源、建立 checkout 與準備依賴。
- `running`：執行器處理固定需求。
- `testing`：引擎獨立執行設定的測試。
- `ready`：提交與本機審查包已準備好。
- `publishing`：交付中，或遠端寫入結果需要重新核對。
- `review`：PR 已核對，交給使用者審查。
- `merged`：GitHub 回報 PR 已合併；不等同於已部署或產品目標達成。
- `closed`：GitHub 回報 PR 已關閉但未合併；不自動重新開發。

另有 `failed`、`interrupted`、`cancelled` 與 `waiting`。`waiting` 用於已辨識的 Codex 額度、請求頻率或登入問題；同時停止新的模型派工。明確執行 `resume --codex` 後，等待任務才回到 `queued`。開發交付停在待審，後續唯讀追蹤會記錄合併或關閉；產品成效的回饋循環屬於後續階段。

PR 的 GitHub 檢查結果與原本機驗證分開保存。遠端版本或合併目標改變時，總覽會指出原驗證與目前內容的差異；沒有檢查不顯示為通過。讀取失敗保留舊觀察並標示過期，恢復後再更新。相同觀察不重複新增事件。

## 後續交付順序

1. **自主執行驗收**：在 Codex CLI 用量可用時，另選一個有明確完成條件的任務，補驗模型實際修改、測試及 Draft PR 的完整流程。
2. **可靠的持續運作**：0.2 已加入有限前景連續模式、可持久保存的暫停、服務錯誤分類與每日嘗試容量；後續加入常駐服務、程序租約、異常恢復與可核對的 token／費用限制。
3. **減少審查負擔**：0.3 已加入 PR 檢查、審查、衝突、合併／關閉追蹤與需處理清單；後續加入獨立程式碼審查、有限修復循環，以及外部成果通知。
4. **跨專案決策**：保存目標、依賴、停滯原因與成果，限制同時推進的專案數。
5. **主動演進**：接入使用者回饋與產品指標，讓候選工作連結到真實目標，而不是不斷產生更多待辦。

## 成效標準

每週少花多少時間重新交代背景、多少任務真正通過審查、需要介入幾次，以及改進是否達到專案目標。提交數、模型活動量與新增任務數不能代替有用成果。
